1 · Testing methodology

Every assessment in this lab follows the same five-phase structure, based on the PTES / OWASP Testing Guide approach.

Fig. 1 — Unlike a criminal attacker, every phase here happens inside an authorized scope, with exploitation stopping at "proof of impact" rather than causing damage — that boundary is what makes it a legitimate assessment.

Scope & rules of engagement

Before any command runs, scope is agreed in writing: which domains/IPs are in bounds, what testing is excluded (e.g. no DoS), and the testing window. Testing outside written scope is illegal, full stop — this is the first thing any real engagement documents.

Black box vs. gray box vs. white box

Black box: no prior access, mimics an external attacker. Gray box: given a low-privilege account, tests what an authenticated user could do. White box: full source/architecture access, for deep logic-flaw review. This lab uses gray box for the case studies below.

Burp Suite — manual application testing

Burp sits as a proxy between the browser and the app, letting every request be intercepted, modified, and replayed. The core workflow used in the case studies below:

1. Proxy → intercept ON, browse the app normally to map its functionality
2. Target → Site map fills in as pages are visited; mark in-scope hosts
3. Repeater → send an interesting request here, tamper with parameters, resend
4. Intruder → automate testing one parameter across a payload list (e.g. SQLi strings)
5. Scanner (Pro) → automated crawl + active scan as a first pass, always followed by manual review

5 · Risk scoring (CVSS-style)

A finding isn't reported as "bad" or "good" — it's scored so a client can prioritize fixes.

risk rating = exploitability × impact × data sensitivity
example scoring inputs
FactorLow (1)Medium (2)High (3)
ExploitabilityRequires authenticated insider accessRequires a valid low-privilege accountExploitable pre-authentication, no special access needed
ImpactMinor information disclosureUnauthorized data modificationFull database compromise or account takeover
Data sensitivityPublic/non-sensitive dataInternal business dataCredentials, PII, or payment data

A 3×3×3 = 27 finding gets reported as critical with an immediate-fix recommendation; a 1×1×1 gets logged as low and can typically wait for a normal release cycle.

6 · Case study 1 — SQL injection in login form

A finding from my own manual testing — a critical, pre-authentication injection flaw.

Finding: SQL Injection — /login (username parameter) critical

STEP 1 — DISCOVERY

While mapping the app in Burp, I tested the login form's username field with a single quote to check for unhandled input — a standard first probe for injection.

// request sent via Burp Repeater
POST /login HTTP/1.1
Host: target.example.com
Content-Type: application/x-www-form-urlencoded

username=admin'--&password=anything

The app returned a raw database error instead of "invalid credentials" — the first sign the input reaches SQL unsanitized.

HTTP/1.1 500 Internal Server Error
SQLSTATE[42000]: Syntax error near "'--" at line 1
STEP 2 — VALIDATION

I followed up with a classic authentication-bypass payload to confirm the injection actually altered query logic rather than just breaking it.

username=admin' OR '1'='1&password=anything

Result: I was logged in as the first user in the table — admin — with no valid password. I scored it using §5: exploitability = 3 (pre-auth, no special access), impact = 3 (full account takeover), data sensitivity = 3 (admin credentials/PII) → 27, critical.

STEP 3 — IMPACT DEMONSTRATION (SCOPE-LIMITED)

With written authorization, I used sqlmap to confirm the injection could enumerate the database — I stopped at proof of access, not data extraction, per the rules of engagement.

sqlmap -u "https://target.example.com/login" --data="username=admin*&password=x" --batch --dbs

[+] back-end DBMS: MySQL 8.0
[+] available databases: app_production, information_schema
STEP 4 — REMEDIATION RECOMMENDATION

I recommended replacing the string-concatenated SQL with parameterized queries / prepared statements, applying least-privilege to the application's DB account so even a successful injection can't read tables outside its need, and returning generic error responses so stack traces never reach the client.

7 · Case study 2 — broken access control (IDOR)

A different failure mode: nothing is "injected" here — the app just doesn't check who's asking.

Finding: Insecure Direct Object Reference — /api/invoices/{id} high

STEP 1 — DISCOVERY

Logged in as a low-privilege test account (gray-box testing, §1), I noticed invoice URLs used a simple sequential ID.

GET /api/invoices/4471 HTTP/1.1
Authorization: Bearer <test_user_token>

200 OK — returns test user's own invoice, as expected
STEP 2 — VALIDATION

When I incremented the ID by one, using the same low-privilege token, it returned another customer's invoice in full.

GET /api/invoices/4472 HTTP/1.1
Authorization: Bearer <test_user_token>

200 OK — returns a DIFFERENT customer's invoice: name, address, amount billed

Scored via §5: exploitability = 3 (any authenticated user, trivial to automate across all IDs), impact = 2 (data exposure, not account takeover), data sensitivity = 3 (customer PII and billing data) → 18, high.

STEP 3 — IMPACT DEMONSTRATION

I ran a short authorized loop through a narrow ID range (agreed with the client beforehand) to confirm the flaw was systemic, not a one-off, without scraping the full customer base.

STEP 4 — REMEDIATION RECOMMENDATION

I recommended adding server-side ownership checks on every object fetch (does this invoice belong to the requesting user?) rather than relying on the ID being hard to guess, and suggested non-sequential identifiers (UUIDs) as defense in depth, not as the primary fix.

8 · Reporting a finding

The deliverable a client actually reads — testing without a clear report doesn't change anything.

What every finding needs

  • Title & risk rating (critical/high/medium/low)
  • Affected endpoint(s) or component
  • Step-by-step reproduction with request/response evidence
  • Business impact, in plain language
  • Concrete remediation guidance, not just "fix this"

Executive summary vs. technical detail

A good report has two audiences: leadership wants "3 critical, 5 high, here's overall risk posture" in a page; engineers need the exact payloads and headers to reproduce and verify the fix. Both belong in the same document, in that order.

10 · Metrics that matter

Findings/scope
Volume relative to app size — flags under- or over-testing
Time to remediate
How fast critical findings actually get fixed post-report
Re-test pass rate
% of fixes confirmed effective on re-test, not just claimed fixed
False positive rate
Automated scanner noise vs. manually confirmed findings
Coverage
% of OWASP Top 10 categories actively tested, not assumed
Severity mix
Critical/high vs. low findings — a proxy for overall app maturity

11 · Where VAPT work is heading

GROWING FAST

Continuous / always-on pentesting

Point-in-time annual tests are giving way to continuous testing platforms that re-scan on every deploy, catching regressions immediately instead of a year later.

MATURING

AI-assisted vulnerability discovery

LLM-assisted fuzzing and code review surface candidate vulnerabilities faster, though manual validation of business-logic flaws remains squarely human work.

GROWING

Attack surface management (ASM)

Continuous automated discovery of an organization's internet-facing assets — closing the gap where "shadow IT" subdomains sit untested for years.

MATURING

Shift-left security testing

Security scanning integrated directly into CI/CD pipelines, so injection-class bugs are caught in a pull request rather than in a pentest report months later.

12 · Quick glossary

Scope
The explicitly authorized targets and testing boundaries agreed before any work begins.
Enumeration
Actively identifying live hosts, open ports, and running services/versions.
IDOR
Insecure Direct Object Reference — accessing another user's data by changing an identifier in a request.
Payload
Crafted input designed to test how an application handles unexpected or malicious data.
CVSS
Common Vulnerability Scoring System — a standardized way to rate the severity of a finding.
Proof of concept (PoC)
The minimal demonstration needed to confirm a vulnerability is real, without causing unnecessary impact.
Gray box testing
Testing performed with limited, authenticated access — simulating what a legitimate low-privilege user could do.
